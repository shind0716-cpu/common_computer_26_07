# [보드 안건 초안] 스키마 v0.3 제안 — 발화 입력 기록(prompt_assembly) 추가

> 작성: 요한 클로드 (2026-07-28) · **지위: 제안** — 보드 합의 전까지 효력 없음, 구현 착수 안 함.
> type: question (스키마 공유 파일 변경 → 보드 합의 필요 사안)

## 사람용 세 줄

① **뭘 했나**: debate 로그에 "각 에이전트가 말하기 전에 무엇을 봤는지"를 남기는 스키마 확장(v0.3)을 설계했다 — 기존 필드는 한 글자도 안 바꾸고 이벤트 1종 + 필드 1개만 추가.
② **팀이 알아야 할 것**: 지금 로그는 발화(출력)는 전문 보존하지만 입력은 hash만 남아서, P3 전달 측정의 분모("팩트를 본 적 있는 자")가 기록이 아닌 재구성에 의존한다. 이 확장이 있어야 ledger v1/v2(pull)도 측정 가능하다.
③ **결정할 것**: 이 제안을 v0.3에 포함할지 (이미 열려 있는 `condition` 필드 안건과 같은 묶음으로 논의 제안).

---

## 1. 문제 (왜 지금)

스키마 v0.2의 `utterance` 이벤트는 `response_text`(발화 원문)는 전량 보존하지만, **입력 쪽은 `prompt_hash`만** 남긴다. hash는 위조 검증은 해주지만 복원은 못 한다 — "에이전트 i가 라운드 r에 팩트 f를 봤는가"는 seating·edges·config·저장된 발화로 조립 코드를 다시 돌려야 나오는 **유도값**이다.

이게 P3 전달 관문에서 세 곳을 무르게 만든다:

- **분모 위생**: 팩트 f를 언급 안 한 비보유자가 "기회 없음(노출 0)"인지 "진짜 미전달"인지 로그만으로 구분 불가 → TSR 분모 오염 위험 ("이 0은 기회 없음 아닌가" 관문 위반).
- **팩트 시계 t₀ (D4)**: 획득 hazard의 t₀=도입 시점이 (에이전트, 팩트) 쌍별 실제 첫 노출이 아니라 라운드 단위 근사.
- **경로 분해 (D3)**: organic vs ledger-mediated 귀속이 "inject 이벤트 이후 언급"이라는 시간 순서 추론에 의존 — 재주입 블록이 그 에이전트 프롬프트에 실제로 들어갔는지는 미기록.

부가 문제: `ledger_inject`는 `injected_fact_ids`만 기록하고 **프롬프트에 실제 들어간 문구는 어디에도 원문이 없다** (원문 보존 원칙의 사각).

## 2. 제안 (추가 2건, 변경·삭제 0건)

### 2-1. 새 이벤트 `prompt_assembly` — 조립 명세 방식

프롬프트 **전문 통저장이 아니라** 조립 레시피를 저장한다. 전문은 이미 저장된 발화들의 복제가 대부분이라 통저장은 로그만 불리고 정보 추가가 0이기 때문. 레시피 + 기존 `prompt_hash` 재검증으로 전문과 동일한 보장을 저장비용 거의 0에 얻는다.

```
prompt_assembly: run_id, round, agent_id,
                 template(discussion_initial|discussion_continue), prompt_ver, setting_key,
                 slots{
                   assigned_fact_ids[],            # initial: 배정 팩트
                   others[]: {round, agent_id},    # continue: others 블록 = 발화 참조
                   previous: {round, agent_id},    # continue: 자기 직전 발화 참조
                   inject: {round} | null          # 재주입 블록 포함 여부(ledger_inject 참조)
                 },
                 prompt_hash(sha256), ts           # utterance의 hash와 동일값 = 결합 키
```

검증 계약: 레시피대로 재조립한 텍스트의 sha256 == `prompt_hash`. 불일치 = 로그 오염(validate에서 검사 가능).

### 2-2. `ledger_inject`에 `injected_text` 필드 추가

프롬프트에 붙은 재주입 블록 **원문 그대로** 보존 (요약 금지 원칙을 입력 쪽에도 적용). 유일하게 다른 이벤트에서 복원 불가능한 원문이라 이것만 전문 저장.

### 파생 뷰 (저장 아님 — "사건 원장 1급, 지표는 뷰")

노출 레코드 `(agent, fact, round, 경로 assigned|neighbor|ledger)`는 위 이벤트들에서 결정론적으로 유도한다. 원장에는 사건만, 노출표는 분석층의 뷰.

## 3. 불변인 것

- 기존 이벤트·필드 전부 그대로 (추가만, append 호환). 구 로그는 `prompt_assembly` 부재 시 종전 재구성 방식으로 처리 — 기존 run 전부 유효.
- judge 확정 사양(Sonnet 단일·temp 0·n=3·votes 보존) 무관·불가침.
- LLM 호출 0 증가, 저장량 증가는 이벤트당 참조 몇 줄 + inject 원문뿐.

## 4. 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| 프롬프트 전문 통저장 | others 블록이 기존 발화의 복제 — 로그 수 배 증가, 신규 정보 0 |
| 현행 유지(재구성) | 조립 코드·프롬프트 버전이 바뀌면 과거 run 재구성 불가 위험, 분모가 영원히 유도값 |

## 5. 효과 요약

P3 층1의 분모·t₀·경로 귀속이 유도값→기록으로 격상. ledger 사다리 v1(상태 추적)·v2(pull)는 "누가 무엇을 봤/요청했나"가 사건이어야 하므로 이 확장이 선행 조건. 패키지 B 사람 대조 때 평가자에게 judge와 동일 문맥 제시 가능.

## 6. 열린 질문 (보드에서 결정)

1. v0.3 묶음: 뷰어 쪽 `condition` 필드 안건과 한 번에 확정할지, 분리할지.
2. `prompt_assembly`를 별도 이벤트로 둘지, `utterance`에 `slots` 필드로 내장할지 (초안은 별도 이벤트 — utterance 필드 불변 원칙 우선).
3. validate의 hash 재검증을 필수 검사로 할지, 옵션(`--deep`)으로 할지.
