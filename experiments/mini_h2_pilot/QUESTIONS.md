## v1 설계 질문 (선별 재주입·상태 추적의 전제 검증)

**Q1. 재주입된 팩트는 실제로 재발화되는가? (재발화율)**
- 정의: inject(r)에 포함된 팩트 중 stage r 판정에서 SURVIVING인 비율.
- 판독: `q1_reuptake` — 라운드별 {injected, revived, rate}.
- v1 함의: 재발화율이 낮으면 "전량 재게시"는 프롬프트만 태우는 것 → 선별·강조 방식 필요.

**Q2. 재발화된 팩트는 다음 라운드에 또 죽는가? (재소실률)**
- 정의: inject(r)에서 살아난 팩트가 stage r+1에서 다시 소실인 비율.
- 판독: `q2_relapse` — {revived_at_r, dead_at_r1, rate}.
- v1 함의: 재소실률이 높으면 v0은 라운드마다 같은 팩트를 영원히 재주입(진동) →
  v1의 상태 추적(한 번 살린 팩트의 이력)이 필요하다는 직접 근거.

**Q3. inject 블록은 얼마나 커지는가? (프롬프트 부풀림 궤적)**
- 정의: 라운드별 injected_fact_ids 수와 재주입 블록 문자 수.
- 판독: `q3_block_growth` — [{round, n_facts, n_chars}].
- v1 함의: 블록이 프롬프트 본문 대비 비대하면 전량→선별 전환의 비용 근거.

**Q4. 장부 언급인가 자생 언급인가? (경로 분해 예습 — P3 D3와 동일 질문)**
- 정의: stage r의 신규 언급(r-1 미언급→r 언급)을 [당회 inject 포함 여부]로 이분.
- 판독: `q4_pathways` — {ledger_linked, organic, off_arm_organic(대조)}.
- v2 함의: ledger_linked가 지배적이면 push(재주입)가 유효 채널 → pull 설계는
  "요청 비용"을 정당화해야 함. organic이 지배적이면 push 효과 자체 재검토.
